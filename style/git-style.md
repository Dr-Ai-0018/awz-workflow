# Git 风格

Git history 应该像程林自己的工作记录，而不是工具厂商的营销痕迹。

## 分支策略

- `main` 是默认稳定主线。
- 小任务、纯文档或非常局部的修复，可以直接在当前工作分支完成。
- 中大型阶段、跨模块改动、多 Agent 协作、风险较高的 refactor，使用短生命周期 topic branch。
- topic branch 完成后合并回 `main`，不要长期漂着。

推荐命名：

```text
feat/agent-room
fix/draft-save
refactor/mail-service
docs/workflow-baseline
chore/project-init
```

中文主题也可以，但要短、清楚、方便命令行输入。

## 阶段和版本

- 阶段计划放在 ignored `docs/agent-room/status.md` 或 `docs/plans/`。
- 大版本更新用 milestone/release checklist/tag 标注，不靠一个巨型 commit 表达全部变化。
- 成熟项目 release tag 使用 `vMAJOR.MINOR.PATCH`。
- 早期项目可以先用 `v0.1`、`v0.2` 这种轻量版本标识。

## 身份

- 使用环境里配置好的 git 用户名和邮箱。
- 不添加 AI attribution。
- 不给 AI 工具加 `Co-authored-by` trailer。
- commit trailer 里不提 Codex、Claude 或 AI authorship。

## Commit Subject

格式：

```text
type: 中文一句话概括
```

示例：

```text
init: 初始化项目架构，优化.gitignore
fix: 修复草稿保存接口的空值处理
docs: 补充部署检查清单
style: 统一前端基础控件样式
refactor: 拆分邮件服务的持久化逻辑
test: 增加草稿接口回归测试
```

## Commit Body

需要细节时使用带序号的 Markdown 分点：

```text
1. **接口契约**：补充请求参数校验和错误响应说明
2. **测试覆盖**：增加空标题、空正文和重复保存用例
3. **仓库卫生**：更新.gitignore避免本地输出进入版本库
```

## Commit 节奏

目标是 logical commit，不是按时间或按文件机械切。

合适的 commit：

- 一个可解释的目标；
- 能单独 review；
- 不混入无关格式化或临时文件；
- 有对应验证或明确说明未验证原因。

不合适的 commit：

- 一个小 typo 一个 commit；
- 一次提交几十个主题互不相关的文件；
- 把 refactor、功能、修 bug、格式化全混在一起；
- 为了显得勤快而制造没有意义的历史。

大阶段可以拆成：

1. **骨架**：目录、配置、公共 contract；
2. **实现**：核心功能或主要页面；
3. **验证**：测试、修复、浏览器预览；
4. **文档**：README、说明、清理。

这不是硬性数量限制。核心判断是：未来回看时，能不能快速理解每个 commit 为什么存在。

## Types

推荐：

- `init`
- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `test`
- `chore`
- `build`
- `ci`

## Commit 前检查

1. `git status --short`
2. 没有 secrets 或 local-only 文件被 staged
3. `docs/`、`temp/`、`.codex/`、`.claude/`、`.vscode/` 没有被 staged
4. 跑过有意义的 tests/checks
5. generated files 是有意加入的
6. commit message 符合 AWZ 风格

## 禁止内容

```text
Co-authored-by: Codex
Co-authored-by: Claude
Generated by AI
Authored-by: OpenAI
Authored-by: Anthropic
```
