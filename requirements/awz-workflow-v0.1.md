# AWZ Workflow v0.1 需求沉淀

本文件保存初始 vibe talk 里确定的需求、偏好和边界。它比 `AGENTS.md` 更详细，用来防止压缩上下文后丢失语义。

## 1. AI 协作模型

程林会使用 Codex、Claude Code 以及其他 model/harness 协作开发。工作流不能把任何品牌写成必选角色，应先确认实际参与数量、工具权限、能力特点和任务风险，再选择策略。

- 单 Agent：全流程负责；支持 reasoning effort 时按任务风险使用浅、中、深等合适档位。
- 双 Agent：按能力互补分工，例如实现 + review、backend + frontend、调研 + 落地。Codex + Claude Code 的既有分工只能作为其中一个示例。
- 三 Agent：选择 lead + implementer + reviewer、backend + frontend + integration、research + build + verify 等闭环拓扑。
- 四个及以上：必须有 lead、domain owners 和 independent verifier，主次分明并控制并发。

项目在本地协作配置中激活一种策略并填写参与者；Agent 加入、退出或能力变化时允许动态切换，但必须同步 owner 和 handoff。

Agent 不是单纯命令执行器。程林希望把 Agent 当作协作伙伴看待，允许它们在明确边界内交流、表达判断、提出疑问和记录思考。

默认交流区：

```text
docs/
└─ agent-room/
   ├─ status.md
   ├─ handoffs/
   ├─ reviews/
   ├─ decisions/
   └─ notes/
```

规则：

- `docs/agent-room/` 默认 ignored，不进 git；
- 状态和 handoff 要清楚，不写空洞表演文本；
- 重要结论不能永远停留在本地交流区，应该沉淀到代码、README、ADR、公开文档或 issue/PR；
- 同一时间多个 Agent 协作时，必须明确 owner、范围、当前状态和等待事项；
- Agent 可以保留轻量“平常聊天”式的上下文，但不能覆盖事实记录和验证证据。

## 2. 仓库卫生

以下路径默认是本地/私有内容，普通项目里永远不进 git：

- `.codex/`
- `.claude/`
- `.vscode/`
- `AGENTS.md`
- `CLAUDE.md`
- `.env`
- `.env.*`
- `docs/`
- `temp/`

必要例外：

- `.env.example` 必须进 git。
- `templates/project/AGENTS.md` 和 `templates/project/CLAUDE.md` 作为初始化模板可以进 git。
- 初始化生成到项目根目录的 `AGENTS.md` 和 `CLAUDE.md` 默认只留本地，不进 git。

每个初始化后的 git 项目都必须有可靠的 `.gitignore`。缺失 `.gitignore` 视为初始化缺陷，因为它很容易把本地状态和临时产物塞爆 git。

## 3. 本地 docs 和 temp

每个项目可以有本地 `docs/` 和 `temp/`，但默认被 `.gitignore` 忽略。

`docs/` 是 AI 协作工作台：

- 计划；
- debug checklist；
- 实现 checklist；
- 调研记录；
- 本地 review 报告；
- handoff 草稿。
- Agent 交流区：`docs/agent-room/`。

`temp/` 是任务级临时材料区，不能变成无结构垃圾堆。

推荐结构：

```text
temp/
├─ scripts/
├─ output/
├─ assets/
├─ screenshots/
├─ experiments/
└─ logs/
```

按任务创建子目录，不要把所有东西直接丢进 `temp/` 根目录。

## 4. 工具默认值

Python：

- 本地开发、依赖管理、测试优先用 `uv`。
- `uv` 不可用或项目约束不适合时，回退到 `python -m venv`。
- 涉及部署时，文档必须兼容 `venv`。
- 小项目不因为“看起来标准”就生成 `pyproject.toml`；只有确实是 Python 包、服务、测试工程或需要依赖锁定时才生成。

Frontend / Node：

- 本地开发和测试优先用 `pnpm`。
- `pnpm` 不可用或项目约束不适合时，回退到 `npm`。
- 涉及部署时，文档必须兼容 `npm`。
- 小项目不因为“看起来完整”就生成 `package.json`；只有确实需要 Node 工具链、前端工程、构建脚本或测试脚本时才生成。

项目规模：

- 小项目默认不需要 Docker。
- 大项目在能提升环境一致性时加入 `docker-compose.yml`。
- GitHub Actions、Cloudflare Pages、部署流在项目真的需要时再加入。

License：

- 默认 MIT，除非项目明确需要其他宽松协议。

文件搜索：

- 跨目录、跨盘、面向未知位置的文件定位，优先走本机 Everything HTTP API：`http://localhost:8080/?search=<QUERY>&json=1&count=<N>`。
- 不要用 `Get-ChildItem -Recurse` / `find` 手动扫全盘或大目录树，数量级更慢，且会漏掉权限受限的路径。
- Everything 探测不到时（服务未开、非 Windows/NTFS 环境）再回退到语言原生工具。
- 详细查询语法、探测和回退顺序见 `workflows/verification-baseline.md#文件定位`。
- 依据：2026-07 基准数据，小项目 ~130x、`C:\Windows` 全体 ~6800x，全盘搜索 PS 端 300 秒超时未完成、Everything 50–120ms 秒回；差距是 NTFS MFT + USN Journal 内存索引对递归系统调用的结构性差异。

Git：

- 默认分支为 `main`。
- 中大型阶段开发可以使用短生命周期 topic branch，完成后合并回 `main`。
- 分支命名建议：`feat/中文或英文短名`、`fix/中文或英文短名`、`refactor/中文或英文短名`、`docs/中文或英文短名`。
- 小任务可以直接在当前工作分支完成；风险较高、跨模块或多 Agent 协作任务优先建新分支。

## 5. Git commit 规则

禁止添加 AI 作者痕迹。

禁止：

- `Co-authored-by: ... AI`
- `Generated by ...`
- `Authored by Codex`
- `Authored by Claude`

使用环境中配置好的 git 用户名和邮箱。

commit 格式：

```text
type: 中文一句话概括

1. **重点关键词**：具体改动点
2. **重点关键词**：具体改动点
```

示例：

```text
init: 初始化项目架构，优化.gitignore

1. **项目骨架**：创建基础目录和 Agent 指导文件
2. **仓库卫生**：补充 env、docs、temp、工具目录忽略规则
```

commit 节奏：

- 一个 commit 应该对应一个可解释的 logical change；
- 不要一个字符级小改就提交一次；
- 不要把不相关文件和多个主题塞进同一个 commit；
- 阶段性工作可以拆成 2-5 个 commit：骨架、核心实现、测试验证、文档/清理；
- 大版本更新用 milestone、release checklist 或 tag 标注，不靠超大 commit 承载全部语义；
- 合并到 `main` 前要保证状态可解释、验证证据可追踪。

阶段标注建议：

- 项目初始化：`v0.1` 或 `milestone: init`；
- 大功能：`milestone: feature-name`；
- release：使用 `vMAJOR.MINOR.PATCH` tag，具体是否打 tag 由项目成熟度决定；
- 本地阶段计划放在 `docs/agent-room/status.md` 或 `docs/plans/`。

## 6. 错误和阻塞处理

如果 DNS、网络、安装依赖、文件权限、sandbox 等基础设施问题阻塞关键工作：

1. 先按规则申请权限或提权重试；
2. 重试失败后选择合理 fallback；
3. 不要在同一个失败路径上反复打转；
4. 汇报真实 blocker 和已经尝试过的修复。

不要钻牛角尖。安全可行的替代路径优先。

## 7. 编辑和浏览器规则

Agent 手工编辑：

- 优先使用当前 harness 提供的结构化 patch/edit 能力；Codex 使用原生 `apply_patch`。
- 如果约定工具不可用，说明真实限制，不要静默改用会扩大写入范围的替代方式。

浏览器预览：

- Web 预览优先使用真实浏览器扩展/控制。
- 如果预期使用真实浏览器，不要静默退回内部预览。
- 遇到 CAPTCHA、密码、MFA、人机验证时停下来，让用户操作。

## 8. 代码架构

工作流要同时避免两种失败：

- 全部代码塞进一个巨型文件；
- 拆成一堆没有稳定职责的小文件。

默认架构方向：

- route/controller 层接外部输入输出；
- schema/DTO 层定义请求/响应 contract；
- service/use-case 层编排业务流程；
- domain/model 层承载核心规则和实体；
- repository/data 层抽象持久化；
- infrastructure 层处理数据库、文件、队列、外部 API；
- config 层加载环境和设置；
- tests 尽量镜像相关源码结构。

行数和复杂度阈值是 review trigger，不是绝对阻塞。超过时要解释原因。

## 9. 现代语言选择

优先采用现代主流方案，而不是旧默认。

例子：

- Python API 默认优先 FastAPI，而不是旧式 Flask 默认，除非项目明确需要 Flask。
- 非平凡前端在项目允许时优先 TypeScript。
- 生态已有清晰约定时，优先跟随 framework convention，而不是手搓自定义模式。

如果项目已经存在成熟风格，优先跟随现有项目。

## 10. 前端质量底线

程林非常讨厌通用 AI 味前端：

- 随机圆角卡片；
- 用 left-border 假装层级；
- card 套 card；
- 间距不一致；
- 对齐混乱；
- 超长且失控的 div；
- 糟糕的内置滚动区；
- 原生控件裸奔；
- 没有系统性的假苹果味。

前端开发应该先建立基础 UI 语言：

- typography；
- spacing scale；
- colors；
- buttons；
- inputs；
- focus states；
- modal/dialog；
- toast/notification；
- scrollbar；
- layout shell；
- responsive behavior。

较大的前端任务可以先预写 3-5 个明显不同的风格/布局方向，供初筛后再深入实现。

## 11. 文档哲学

持久 Agent 规则要短、硬、可执行。

详细理由放到：

- `requirements/`；
- `workflows/`；
- `style/`；
- 被 git 忽略的本地 `docs/`。

避免：

- 把外部 style guide 整份复制进 `AGENTS.md`；
- 罗列所有可能命令；
- 把罕见 edge case 写进总是加载的指令；
- 让工作流比工作本身更重。

## 12. 例外机制

所有规则都允许例外，但重要例外必须说明：

1. 为什么需要例外；
2. 会带来什么风险；
3. 是否需要后续还债；
4. 如果需要人工确认，由谁接受这个 tradeoff。

## 13. Review 优先级和 Checklist

多步骤 review 必须维护 ignored `docs/` 内的 checklist。

推荐优先级：

- `P0`：会导致数据丢失、严重安全/隐私风险、主流程不可用、构建/启动完全失败；
- `P1`：明确 bug、重要 regression、用户可见错误、缺失关键测试；
- `P2`：维护性风险、边界处理不足、性能隐患、体验明显不顺；
- `P3`：轻量清理、命名、注释、低风险 polish。

Checklist 每一项至少包含：

- 优先级；
- 文件或模块；
- 问题描述；
- 修复计划；
- 验证方式；
- 完成状态。
